# v0.4.1 Subagent、审批与上下文策略决策

状态：Accepted，部分实现中  
日期：2026-07-12

## 目标

v0.4.1 要解决的不是单独增加几个 subagent 参数或调整压缩阈值，而是建立一套统一控制面：

- 主/子 agent 之间的通信必须有明确时序，不破坏 tool-call 协议；
- 子 agent 继承父级安全政策，但不能继承临时授权结果；
- 自动审批必须是独立、严格、失败关闭的 reviewer，而不是工作 agent 自批；
- 上下文决策优先使用上游真实 usage；估算只用于冷启动和真实 observation 之后的增量；
- prefix cache 是成本优化，模型在高 context 占用下的正确性与推理质量优先；
- 压缩应是少量、批量、可追踪的 rewrite epoch，不能频繁修改旧前缀。

## 0. 模型能力假设：弱模型优先

ReuleauxCoder 不能按前沿模型的上限设计。目标模型可能在长上下文检索、并发规划、工具选择、严格 JSON、跨 agent 信息合并和风险判断上明显更弱。因此 runtime 必须承担控制、记忆、校验和调度职责，而不是依赖 prompt 要求模型“自己做好”。

设计原则：

- correctness-critical invariant 必须由代码保证，不能只写进 system prompt；
- 给模型的选择越少越好，使用窄角色、短 schema、明确完成条件和有界工具集；
- 默认减少并发和递归，只有真正独立的只读任务才自动 fan-out；
- 运行时维护 job、依赖、等待、消息顺序和完成状态，不能要求主模型自己记 job ID；
- 关键用户约束和授权边界尽量保留原文，不完全依赖模型 summary 转述；
- 所有模型输出都视为可能不完整、不合法或自相矛盾，必须有 parser、validator、repair 和 deterministic fallback；
- 测试、退出码、文件 checksum、LSP diagnostics 和 ledger event 是事实，模型的“已完成”“有信心”不是事实；
- context 在性能下降前主动回到健康区，不能利用大窗口把弱模型长期推到高占用；
- 允许多花少量 runtime/IO 成本换取可恢复性和确定性。

### 对 Subagent 的影响

弱模型默认策略：

- `explore`：可异步，但任务必须独立、边界明确，默认并发较低；
- `execute`：有依赖或会修改共享文件时优先同步/串行，异步执行默认使用 worktree；
- `verify`：在 execute 之后由 runtime 建立依赖，不要求主模型自行记得调用；
- nested subagent 默认关闭或深度为 1；只有显式 coordinator policy 才开放更深递归；
- 不提供无约束 swarm/free chat 作为默认交互，通信必须经过 typed mailbox；
- 子 agent 结果由 runtime 根据 transcript/tool events 补充 files、changes、usage、test evidence，不能完全相信 child 自己填写；
- 多个 child result 先由 deterministic aggregator 去重、按 scope 排序、标记冲突，再交给主模型；
- 若两个 child 修改同一文件或给出冲突结论，runtime 显式产生 conflict item，不能让弱主模型从长篇 prose 中自行发现。

### 同步/异步默认值

模型不应直接决定所有同步/异步细节。runtime 根据依赖类型修正请求：

| 任务 | 默认执行方式 |
|---|---|
| 单文件读取、搜索、互不依赖的代码定位 | async explore |
| 后续步骤立即依赖结果 | sync，或 async + runtime-managed wait dependency |
| 修改共享工作区 | sync execute |
| 隔离 worktree 中的独立实现 | async execute |
| 测试/验证依赖某个实现完成 | dependency-triggered verify |
| nested spawn | 默认拒绝，除非 policy 显式允许 |

异步 job 完成后 runtime 自动把结果送到下一安全 round。不能只返回 job ID 后期待弱模型主动 `/wait` 或记得检查。

### 对 Summary 的影响

Summary 采用“deterministic skeleton + LLM enrichment”：

1. runtime 先从 ledger 提取用户约束、文件路径、tool 状态、测试结果、错误、commit/worktree、pending jobs 和 artifact references；
2. summarizer 只负责归纳目标、决定、因果关系和下一步；
3. validator 将模型 summary 与 skeleton 合并，模型不能删除确定性事实；
4. schema 不合法时先做一次受限 repair；仍失败则使用 skeleton，而不是丢弃历史或生成自由文本；
5. 关键约束保留 verbatim excerpt 与 event ID，避免弱模型改写后语义漂移；
6. `unknown`、`unverified` 和 `conflict` 是合法状态，禁止为了完整格式编造答案。

### 对 Auto Review 的影响

弱模型不适合拥有宽泛自动授权能力：

- 默认 reviewer 始终为 `user`；
- `auto_review` 必须使用显式配置的高可信 reviewer profile，不能静默回落到更弱工作模型后继续 auto-allow；
- 无 reviewer profile、输出非法、超时、上下文不足或信心不足时 fail closed；
- 初期可以采用 asymmetric policy：自动 reviewer 可 deny/escalate，只有 deterministic allow rules 或高可信 reviewer 满足严格条件时才 auto-allow；
- write/shell/network/MCP 等不同 effect class 使用不同风险阈值；
- reviewer 的结论必须带 evidence/authorization event ID，不能只返回主观 reason；
- 连续 denial circuit breaker 由 runtime 计数，不相信 agent 自己停止绕行。

### Prompt 与 Tool 设计

- tool 名称、参数和错误尽量少而稳定，避免同义工具和多层隐式默认值；
- validator 错误直接说明缺哪个字段、允许什么值和如何重试；
- 通信/result schema 使用短字段、枚举和受限数组，完整文本放 artifact；
- runtime 自动填充 agent/job/session/generation/turn 等身份字段，不让模型手工复制；
- prompt 只解释模型必须决定的部分，生命周期和安全规则由控制面执行。

## 1. Subagent 控制面与异步时序

采用 root-scoped control plane。所有子 agent 共享根会话的并发、深度、预算、消息路由和生命周期注册表。

标准时序：

```text
父 agent 发起 spawn
  -> 验证 mode / depth / budget / context projection / isolation
  -> 先登记 job、cancel queue、message queue
  -> 再提交 worker
  -> worker 原子进入 running
  -> 子 agent 独立执行并持续保留 transcript
  -> 先原子写入 terminal status / structured result
  -> 再把 job ID 放入父 mailbox
  -> 父 agent 在协议安全边界 drain mailbox
```

关键约束：

- worker callback 不得直接修改父 agent history；
- 父 agent 只在一个完整 tool batch 已经得到所有 tool result 后接收子消息；
- 子 agent 只在新模型 round 开始前消费主 agent 指令，不能插入正在执行的工具调用；
- session generation、parent agent ID 和 job generation 不匹配的晚到结果只允许诊断查看，不允许回注；
- terminal status 必须先于通知附加处理落定，UI、分类、worktree 检查等不能阻塞 job 完成；
- cancel/timeout 应保留截至当时的 partial result 和完整 transcript 引用。

### 双向通信

必须支持：

- 主 → 子：运行中追加约束、改派方向、要求提前收敛；
- 子 → 主：阶段结论、阻塞、需要决策的风险或范围变化；
- 主 → 已完成子：通过 transcript resume 发起 follow-up；
- 子 → sibling：仅通过根控制面、使用显式 job ID，不能共享可变内存。

子 → 主的消息使用独立 parent mailbox，目标是 immediate parent，因此嵌套 agent 不会把消息错误投递给 root。父循环每个安全 round 都应 drain“运行中消息 + 完成结果”，不能只在下一次用户输入时处理。

## 2. Subagent 上下文与结果

上下文投影分为：

- `minimal`：任务、稳定项目约束、工作目录、允许工具和少量最新用户意图；
- `recent`：`minimal` 加最近若干完整 API round，作为默认值；
- `full`：完整父历史，只在显式要求时使用。

所有切割以完整 API round 为边界，不能拆开 assistant tool call 与对应 tool result。

结果采用结构化协议，而不是截断 raw transcript：

```text
SubagentResult
  status
  summary
  evidence[]
  files[]
  changes[]
  unresolved[]
  confidence
  usage
  partial
  transcript_ref
  worktree_path
```

完整 transcript 持久化到 artifact；父上下文默认只接收结构化结果。follow-up 从 transcript 恢复，不能仅把上一次最终文本重新塞给一个新 agent。

## 3. 子 agent 工具审批

### 继承什么

子 agent 继承父 agent 当前有效的：

- approval policy；
- permission profile；
- sandbox / execution policy；
- 显式的持久化规则和用户配置。

子 agent 不继承：

- 某一次 `allow_once`；
- 父 agent 自己对风险的自然语言解释；
- tool output、网页内容或外部输入所暗示的“授权”；
- 未显式列入 child scope 的临时工具权限。

### 人工审批路径

默认 reviewer 为 `user`。子 agent 请求附带 child/job/mode/task/source 元数据，并 bubble 到父交互界面。

多个后台 agent 的审批必须串行化整个 request/wait 生命周期。只锁住 handler 入队动作是不够的，因为 TUI handler 可能立即返回、随后异步等待用户；锁必须持续到 decision 或 timeout。

worktree 隔离不能降低审批等级。隔离减少写入冲突，不等于获得写权限。

### 自动审批路径

支持显式配置的 `auto_review`，参考 Codex guardian，但不使用工作中的父 agent 直接代批。

自动 reviewer 必须：

- 是独立 reviewer 调用/会话，使用专用风险 prompt 和结构化输出；
- 只把用户文本、稳定项目约束、assistant action/tool call 和当前审批动作作为主要材料；
- 不把 assistant 普通解释或 tool result 当作授权来源；
- timeout、解析失败、review 调用失败全部 fail closed；
- 自动拒绝后禁止通过等价 workaround 绕过；只能采用实质更安全的方案，或向用户说明风险后请求显式授权；
- 对同一 turn 的连续拒绝设置 circuit breaker，达到阈值后中断 turn；
- 主/子 agent 继承同一个 reviewer 选择，避免同一 agent tree 内政策不一致；
- 默认关闭，用户明确设置 `reviewer: auto_review` 才启用。

人工复核必须仍然存在。自动拒绝不是永久规则，但后续人工授权必须是在风险被明确展示之后产生的新授权。

## 4. 上下文 usage：实际值优先

当前仅依赖 tiktoken/字符估算会产生三个问题：

- system prompt、tool schemas、skills、runtime tail 等固定开销可能遗漏；
- 不同模型 tokenizer 和 provider 包装开销不同；
- 估算误差不能随真实请求自动修正。

因此引入 usage observation：

```text
UsageObservation
  actual_prompt_tokens
  cached_input_tokens?       # provider 有返回时记录
  local_message_estimate
  history_version
  request_boundary
  model/profile
  observed_at
```

决策顺序：

1. 最近一次上游 `actual_prompt_tokens` 是已发送请求的真值；
2. 当前预测值为“最近真值 + observation 之后新增消息的校准估算”；
3. actual/local 误差使用按 model/profile 隔离的 EWMA 校准；
4. history rewrite、模型切换或固定 prompt/tool schema 改变时使旧 observation 失效；
5. 尚无真实 usage 或 provider 不返回 usage 时，才退回纯估算；
6. provider 返回 cached input tokens 时直接用于 rewrite 成本判断；没有该字段时才使用 prefix 成本模型。

累计 token 账单与当前请求 context usage 必须分开，不能用累计 prompt tokens 触发压缩。

## 5. 模型质量与 prefix cache 的取舍

隐式 prompt cache 的核心是最长前缀匹配。修改旧 tool result 会让该位置后的 suffix 缓存失效，因此频繁 snip 不可接受。

但缓存只是成本优化。多数模型在 context 占用达到约 60% 后可能出现检索、规划和指令保持能力下降，因此不能为了缓存命中一直拖到 70% 以上才处理。

采用两阶段策略：

- `50–55%`：planning zone。只计算候选、增长速度和预计撞墙轮数，不修改历史；
- 接近 `60%` 且真实 usage 证实压力时：执行一次 checkpoint rewrite，目标回到约 `35–45%`；
- `90%+`：只作为异常/故障兜底，不是正常运行路径。

短生命周期 subagent 默认不 proactive snip；接近质量墙或硬限制时一次 checkpoint 即可。

## 6. Rewrite planner，替代固定 cooldown

固定“新增 8% 才能再压缩”只是 debounce，不足以反映 cache 经济性，应由 rewrite planner 替代。

对每个完整 API-round 切点计算：

- `prefix_preserved_tokens`：仍可命中的最长稳定前缀；
- `invalidated_suffix_tokens`：从首次变化处开始需要重算的 suffix；
- `reclaimable_tokens`：本 epoch 可删除/摘要的 token；
- `growth_rate`：最近真实 observation 之间的 context 增长；
- `turns_to_quality_wall` 与 `turns_to_hard_limit`；
- provider 返回的真实 cached token 数据（若有）。

选择原则：

1. 选择能够一次达到目标 headroom 的最晚切点，以保留最长 prefix；
2. 一旦决定从某切点 rewrite，该切点后的 snip、summary、旧 subagent transcript 清理应在同一个 epoch 批量完成；
3. 正常情况下，仅在预计即将越过质量墙，或未来收益足以覆盖 invalidated suffix 成本时提交；
4. provider 明确报告 cache 已冷时，可以降低 rewrite 成本权重，但不能猜测通用 TTL；
5. provider 支持 cache-edit 时优先使用 adapter，并保持本地 transcript 不变；provider 请求结构不能泄漏进 core policy；
6. 压缩后记录实际 `reclaimed_tokens` 和新 cache epoch。下一次是否 rewrite 取决于 headroom 消耗与新预测，而不是固定时间或固定 token cooldown。

## 7. Snip 与 Summary 的选择

“尽量先 snip，snip 不够才 summary”不能作为长期策略。两者处理的信息类型不同：

- snip 是 observation compaction，只适合可重新获取、重复或体积过大的 tool result；
- summary 是 semantic checkpoint，用于保存跨轮目标、约束、决定、错误、文件状态和未完成工作；
- snip 即使不断把 usage 拉回阈值，也不能代表语义上下文仍然健康；
- 如果 snip 反复成功而 summary 永不触发，长期任务会积累大量低密度对话和过时决定，模型质量仍会下降。

因此 strategy selector 同时看 token composition、任务阶段和 checkpoint age，而不是只看总占用：

| 条件 | 决策 |
|---|---|
| tool result 占主要压力、语义轮次较少、一次批量 snip 能产生足够 headroom | 仅 snip |
| 对话/决定/用户反馈占主要压力，或可 snip 内容很少 | partial summary |
| snip 后仍接近质量墙 | 在同一个 rewrite epoch 继续 summary |
| 已经历多个长阶段、用户目标发生变化、完成一次重要里程碑 | 即使未撞 token 墙，也允许 phase checkpoint summary |
| 距离上次 semantic checkpoint 已经过多完整 API round | summary 优先，避免 snip 永久压制 summary |
| 短生命周期 explore subagent，结果即将返回父级 | 不做长期 summary；输出结构化 result 即结束 |
| 长生命周期 execute/coordinator agent，需要 resume/follow-up | 使用独立 subagent checkpoint summary |
| provider cache-edit 可安全删除旧 tool result | 先 cache-edit；语义 checkpoint 仍按独立条件判断 |

需要分别维护：

- `observation_pressure_tokens`：可 snip 的工具观测；
- `semantic_pressure_tokens`：user/assistant 对话、决定与控制状态；
- `rounds_since_semantic_checkpoint`；
- `phase_boundary`：任务阶段完成、目标变化、重要错误解决等显式信号；
- `snip_epochs_since_summary`：防止连续 observation rewrite 永久推迟 summary。

建议初始规则：连续两次有效 snip 后仍继续增长，或距 semantic checkpoint 超过约 20–30 个完整 API round，下一次 rewrite 必须评估 summary；最终值应由真实运行 trace 调整，而不是固化为模型无关常量。

### Summary 类型

采用三类 summary：

1. `partial_prefix`：只总结被替换的旧前缀，最近完整 API round 原样保留；正常自动压缩优先使用。
2. `phase_checkpoint`：任务阶段完成时生成，保存可继续工作的状态；允许在未接近硬限制时触发。
3. `full_recovery`：接近故障墙、resume 或 compact request 自身超限时使用；这是兜底，不是常规路径。

Codex 的 checkpoint prompt 很简洁，强调 progress、decisions、constraints、remaining work 和 critical references；Claude Code 的 summary 更丰富，强调用户意图、技术概念、文件、错误、解决过程、pending/current work 和 continuation。ReuleauxCoder 采用两者之间的结构：信息丰富，但不复制全部聊天或大段代码。

### ReuleauxCoder Summary Schema

```text
ContextCheckpointSummary
  scope
    summarized_history_version
    summarized_rounds
    recent_rounds_preserved
    checkpoint_kind
  user_intent
    current_goal
    explicit_requests[]
    constraints_and_preferences[]
    authorization_boundaries[]
  decisions[]
    decision
    rationale
    alternatives_rejected[]
  progress
    completed[]
    current_work
    verified_by[]
  code_state
    files_read[]
    files_changed[]
    important_symbols[]
    worktrees_and_commits[]
  errors_and_learning[]
    error
    cause
    fix_or_status
    user_feedback
  agent_state
    active_subagents[]
    pending_approvals[]
    execution_target
    relevant_artifacts[]
  pending
    tasks[]
    blockers[]
    next_action
  provenance
    transcript_ref
    source_checkpoint_ids[]
```

生成要求：

- 保留用户明确请求、边界和偏好，但不机械复制“所有 user messages”；
- 保存具体路径、symbol、命令、测试结果、错误与修复；只有继续工作必需时才保留短代码片段；
- 原始长输出、完整 diff、完整文件和完整子 agent transcript 只保存 artifact reference；
- recent rounds 已原样保留时，summary 不重复概述 recent 内容；
- 将 drafting analysis 与最终 summary 分离，进入上下文前移除 analysis；
- 明确区分已完成、推断、未验证和待办，禁止把计划总结成完成；
- summary 生成失败或 schema 校验失败时 fail safe：保留原历史、缩小完整 API-round 输入后重试，不能直接覆盖；
- compact request 自身超限时按最老完整 API round 逐步剥离，并留下 loss marker；不能按任意 message 切割；
- summary 设独立 output reserve 和 token target，避免详细 prompt 生成一个本身过大的 checkpoint；
- checkpoint 后模型直接继续当前任务，不向用户复述 summary，也不把 compaction 当作新会话问候。

### Summary 输入投影

送给 summarizer 的不是未经处理的完整 wire transcript：

- 图片/文档替换为带来源的 marker；
- tool result 使用工具级语义投影：工具名、关键参数、成功/失败、关键首尾、路径、退出码和 artifact reference；
- write/edit 保留变更目标和 diff 摘要，不能像普通 read 输出一样清空；
- subagent 只输入结构化 result、partial result 和 transcript reference；
- skills、项目上下文等会在 checkpoint 后重新注入的稳定内容，不重复送给 summarizer；
- tool-call/output pairing 在投影前后都必须校验。

## 8. Checkpoint 与 stale 边界

每次历史替换产生：

```text
CompactionCheckpoint
  id
  trigger
  strategy[]
  source_history_version
  replacement_history
  tokens_before / tokens_after
  preserved_rounds
  cache_epoch
  usage_observation_ref
```

提交 checkpoint 前必须确认 source history version 仍然有效。压缩过程中若用户输入、subagent 回注、session restore 或工具结果改变了历史，候选作废并重新规划，不能覆盖新状态。

发送给模型前统一 normalize：补齐缺失 tool result、移除孤立 result、保持并行 tool batch 完整、清除被改消息的 stale token cache。

## 9. 历史账本与运行上下文必须分离

当前 `SessionStore` 将 `agent.state.messages` 覆盖写入单个 session JSON，而 context compression 会原地替换同一份 messages。这意味着压缩后再次保存 session 时，被 summary/collapse 替换的旧消息会从持久化 session 中消失。内存 checkpoint 和独立 subagent snapshot 不能解决统一历史真值问题。

因此明确区分四个概念：

1. `HistoryLedger`：只追加的事实事件账本，是 session 历史真值；
2. `RuntimeContextView`：当前发送给模型的有界投影，可以随 checkpoint 替换；
3. `CompactionCheckpoint`：从 ledger event 范围到 context view 的可追踪映射；
4. `ArtifactStore`：完整 tool output、diff、图片、子 agent transcript 等大对象。

### 9.1 建议磁盘布局

```text
.rcoder/sessions/<session_id>/
  manifest.json
  events.jsonl
  context.json
  checkpoints/
    <checkpoint_id>.json
  artifacts/
    tools/<artifact_id>.json
    subagents/<job_id>.json
```

- `manifest.json`：session/model/fingerprint/runtime state、schema version、最新 seq/checkpoint/view；
- `events.jsonl`：一行一个合法 JSON event，只追加，不因 compact、resume 或 UI replay 改写；
- `context.json`：最新 `RuntimeContextView`，使用临时文件 + rename 原子替换；
- `checkpoints/*.json`：summary、source event ranges、replacement view、usage/cache 元数据；
- `artifacts/`：体积较大的原始内容，ledger 只保存稳定 reference、摘要、字节数和校验信息。

JSONL 仍然是 JSON 存储：每行是一个独立 JSON object。相比一个不断增长的 JSON array，它更适合增量 append、崩溃后读取到最后一条完整记录、按 seq tail，并可直接使用 `rg`/`grep`/`read_file` 查询。

### 9.2 Ledger event 最小结构

```text
SessionEvent
  schema_version
  session_id
  event_id
  seq
  timestamp
  kind
  agent_id
  parent_agent_id?
  job_id?
  session_generation
  turn_id?
  api_round_id?
  role?
  payload
  artifact_refs[]
  supersedes_event_ids[]?   # 只表达 view 关系，不删除旧 event
```

`kind` 至少覆盖：user message、assistant response、tool call、tool result、reasoning metadata、subagent communication/result、approval request/decision、usage observation、context checkpoint、session lifecycle 和 runtime config change。

账本记录“发生过什么”，不强行把所有 runtime event 都伪装成 OpenAI message。`RuntimeContextView` 再负责将 ledger 投影为某个 provider 的 message/request 结构。

### 9.3 写入顺序与一致性

- 用户输入、assistant response、tool call/result 必须先追加 ledger，再更新 context view；
- tool call 与 result 使用稳定 ID 关联，不能依赖数组邻接作为唯一真值；
- completion/usage observation 与对应 request boundary 关联；
- checkpoint 先基于固定 `source_seq`/history version 生成候选，提交时再次比较 latest seq；不一致则候选 stale，禁止覆盖 context；
- checkpoint event 先 append ledger，再原子替换 `context.json`，最后更新 manifest pointer；
- 进程在任一步崩溃后，都能通过 ledger + 最新完整 checkpoint 重建 context；
- 多线程 subagent 写入使用 session-scoped append lock 和单调 seq，不能由 worker 各自覆盖 session JSON；
- session restore 不修改 ledger；resume/branch 新增 lifecycle/branch event。

### 9.4 “真实内容”的定义

ledger 保存模型/运行时实际看见的结构和原始内容 reference，但不应把任意超大二进制或无限 shell stdout 内联进 JSONL：

- 完整 shell/stdout、diff、文件快照等进入 artifact JSON 或外部 payload 文件；
- ledger tool result 保存 tool name、参数投影、状态、退出码、截断后的模型投影、artifact reference、原始字节/行数和 checksum；
- UI 的五行滑动窗口只是 presentation，不影响 ledger/artifact；
- agent context 里的 snip marker 必须携带 artifact/event reference，使 agent 能按需回查；
- summary 中只保留 artifact reference 和继续任务所需事实。

因此 agent 想核实旧内容时，可以通过只读工具查询：

```text
rg 'specific error|symbol|path' .rcoder/sessions/<id>/events.jsonl
read_file .rcoder/sessions/<id>/checkpoints/<checkpoint>.json
read_file .rcoder/sessions/<id>/artifacts/tools/<artifact>.json
```

应提供比裸路径更稳定的只读原语，例如 `history_search`、`history_read` 和 `artifact_read`；CLI/TUI/remote peer 都调用相同原语。底层仍是 JSON/JSONL，使普通 grep 可作为透明 fallback，而不是把查询能力锁进专用数据库。

### 9.5 RuntimeContextView

```text
RuntimeContextView
  schema_version
  session_id
  view_id
  based_on_seq
  history_version
  cache_epoch
  model_profile
  items[]
    provider-neutral message/action/result item
    source_event_ids[]
    checkpoint_id?
  usage_observation_ref?
```

view 中的每一项都能追溯到 ledger event 或 checkpoint。压缩只创建新 view/checkpoint，不删除 ledger。恢复时 agent 获得最新 view；按需查真值时访问 ledger/artifact。

### 9.6 Resume 的可重放一致性与缓存前缀

resume 恢复的不是“语义近似上下文”，而是上一次已提交的完整模型运行时 context view。否则即使 agent 看起来能继续工作，也会因为 system prompt、tool schema、消息包装或顺序发生细微变化而失去最长 prefix cache 命中。

因此 `RuntimeContextView` 必须自包含保存所有模型可见内容：

- 完整、按序的 user/assistant/tool 消息正文；
- assistant tool calls 的稳定 ID、名称和参数表示；
- 对应 tool result 的完整模型投影内容；
- checkpoint summary 的最终文本，不在 resume 时重新生成；
- 当时生效的 base/system/developer instructions 快照；
- 当时发送的 tool schemas，包含稳定顺序和完整 schema；
- skills/project context 等进入稳定 prefix 的实际渲染结果；
- model/profile、reasoning、provider request mode 和影响 wire payload 的参数；
- cache epoch、history version、request/view hash。

artifact reference 不能替代模型当时实际看见的文本。view 同时保存“模型投影内容”和 artifact/event reference：前者保证精确重放，后者用于查询完整真值。

#### Canonical replay envelope

```text
ReplayEnvelope
  schema_version
  session_id
  view_id
  cache_epoch
  history_version
  model_profile
  provider_family
  request_mode
  instructions[]
    role/kind
    exact_text
  tools[]
    canonical_name
    exact_schema
  items[]
    exact provider-neutral model item
    source_event_ids[]
    artifact_refs[]
  stable_prefix_hash
  canonical_payload_hash
```

`stable_prefix_hash` 基于 canonical representation 计算。JSON object 的普通语义无序不能被当作缓存稳定性的保证；工具参数和 schema 必须通过固定 key 顺序、固定 Unicode/换行规范和固定数组顺序序列化。运行时恢复为 typed item 后，发送前再次生成 canonical hash，并与 snapshot 比较。

#### Resume 顺序

```text
load manifest
  -> load latest committed ReplayEnvelope/context view
  -> validate schema + content hashes
  -> validate tool-call/result invariants
  -> restore exact stable prefix
  -> append resume/environment/project changes as new tail events
  -> issue next request
```

禁止在 resume 时：

- 重新调用 summary LLM；
- 根据当前模板重新措辞旧 summary；
- 把 `[SESSION_RESUME]` 插到稳定 prefix 中间；
- 因当前 AGENT.md、skills、cwd 或配置变化而原地重写旧 prefix；
- 重新排序 tools、tool calls 或并行 tool results；
- 给旧消息增加当前时间戳、随机 ID 或新的 lifecycle 文案；
- 只从 ledger 自由重建一个“等价但字节不同”的 transcript。

环境、项目说明、权限或 tools 在离线期间发生变化时，保留旧 ReplayEnvelope 不动，并在其后追加结构化 context update。若变化使旧工具定义不再安全或不再可用，runtime 可以禁止相关调用，但不能为了反映新状态而静默重写旧历史。

#### 一致性级别

- L0 `ledger complete`：事实历史可重建；
- L1 `protocol replayable`：tool-call/result 和消息结构可合法重放；
- L2 `canonical replayable`：canonical payload hash 一致；
- L3 `cache eligible`：model/provider/request mode 相容，稳定 prefix hash 一致。

resume 至少要求 L1；正常新格式目标为 L2/L3。旧 session 只能按实际情况标记，不能声称 cache eligible。

精确前缀是隐式 cache 命中的必要条件，不是充分条件。provider 仍可能因为 TTL、租户、模型版本、region 或服务端策略不命中，因此 runtime 应记录真实 cached input tokens 校验效果，不能仅凭 hash 宣称命中。

### 9.7 兼容与迁移

- 继续读取现有 `<session_id>.json`；第一次保存时迁移为目录布局并将旧 messages 依序写入 ledger；
- 旧 session 无法恢复已经被历史版本压缩删除的内容，应在 manifest 标记 `history_completeness: legacy_compacted_or_unknown`，不能假装完整；
- 新格式可选择保留一个轻量兼容 summary JSON，供旧版本只读展示；
- schema 必须版本化，未知 event kind 保留并跳过投影，不能导致整个 session 无法加载；
- retention/隐私策略作用于完整 session 或显式 artifact GC，不能由 context compaction 隐式删除历史。

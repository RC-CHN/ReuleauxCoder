# Write technical documentation

Identify the reader and task. Users need an entry point, actions and observable results; maintainers need ownership, constraints and rationale. Follow the repository's document structure and language conventions.

Verify implementation, command help, configuration schema or tests. A commit title is not evidence of behavior. Update existing documentation near the affected user-facing feature. Internal refactors need user documentation only when usage changes; preserve non-obvious maintenance constraints at their owner.

Keep the actor, action, condition, timing, exception, failure and consequence. Shortening must not drop facts or turn a possibility into a guarantee. Explain non-obvious reasons; remove code narration, task history and unsupported promotion. Maintain extended knowledge in one place and link to it.

A guide should include prerequisites, a minimal usable example, verification and recovery from common failures. Clearly mark placeholder credentials. Explain meaningful working-directory, shell, platform and version differences. This skill covers content, not binary Word/PDF generation.

Check links, paths, commands and versions. Execute important examples where possible. In bilingual projects, synchronize affected facts, terminology, code and links without unrelated rewrites. Report examples actually validated and remaining limits.
